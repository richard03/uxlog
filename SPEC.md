**UXLog** is a desktop application (desktop only – there is no web version) for UX design process logging and cooperation with Figma. All stored data – project data, change history, configuration and connector settings – lives in one embedded SQLite database; on startup it is loaded into memory before anything else, every save is written straight to it (only the records changed or deleted since the previous save, so saving does not slow down as the data grows), and there is no second copy (such as browser storage) that could fall behind – except an emergency backup: when a write to the database fails, the latest value is kept temporarily in the browser storage of the app window and the write is retried (after 5, 15, 30 and then every 60 s). A bar under the header says the changes could not be saved and are backed up, with the error detail, "Try again" and "Save data to file" (all data as YAML into Documents/UXLog, loadable through Import). Once a write succeeds the backup is deleted, the bar disappears and "Try again" confirms it with a message. A backup left over (the app was closed during the outage) is restored on the next start, written to the database and announced. If even the backup cannot be stored (browser storage full), the bar warns that the changes are not saved anywhere and closing the window asks for confirmation. A damaged record in the database (not valid JSON, not an object, not valid text) never prevents the app from starting: on startup such records are moved aside into a separate table (`quarantined_records`, nothing is deleted) and the rest of the data loads normally; a bar under the header says how many records could not be loaded and which (collection/id), with "Save damaged records to file" (their original content as JSON into Documents/UXLog, for manual repair) and "Got it". If the data as a whole cannot be read, the app shows empty data with a red bar saying the data could not be loaded and that nothing is being saved, so the stored data is never overwritten by the empty state; saving resumes as soon as the data loads successfully. Opened in an ordinary web browser, the app only says that it is a desktop application. It operates in a closed environment without internet connection; plugins may add connections such as LLM services or external APIs.

## Data Model

### Entities (per project)
       
**Projects** - name, scope (small/medium/large), priority (High/Medium/Low), phase (Research/Design/Development), notebook history (`notebookHistory`: messages `{ id, createdAt, mode: process|ask, text, answer, status: processing|done|error|saved, error, outcomes[] }`). Last-worked date is recorded automatically. Canvas layout (`canvas`: `{ positions: { "<collection>:<id>": { x, y } }, colors: { "<collection>:<id>": "#rrggbb" }, frames: [{ id, title, x, y, width, height, color }], viewport: { x, y, zoom } }`) is stored on the project. The legacy plain-text `notebook` field is read as the first history message ("original notebook") and moved into the history on the next message.

**Goals** - code, name, description, metrics

**Stakeholders** - name, description, influence level, interest level (Mendelow matrix), attitude to the project (positive/neutral/negative), communication plan (how often, which channel, what they need to know)

**Competition** - name, description, competitor type (direct/indirect), strengths, weaknesses, inspiration

**Hypotheses** - code, name, description, status (untested/tested/refuted), explanation

**Personas** - code, name, status (protopersona/persona), description, motivation, needs, problems, barriers, characteristic quote, target group size, target group value

**Scenarios** - code, name, description, trigger (when the need arises), outcome (when the need is satisfied), frequency, value, MoSCoW rating

**Requirements** - code, name, description, motivation, category (data / function / quality / constraint), MoSCoW rating, explanation (for "Won't have")

**Sources** - code (ZDR-…), name, kind (document / interview transcript / e-mail / other), text (`content`), original file name (`fileName`), added (`createdAt`) and processed (`processedAt`, empty = not processed yet). A source is a document, interview transcript, e-mail or any pasted text the project's records are distilled from. "Add source" offers **Upload file** (pick or drag & drop; Word .docx, PDF with a text layer, .txt/.md and e-mail .eml – subject, sender, recipient, date and the plain-text body, HTML-only mails converted to text, attachments ignored; at most 25 MB) or **Paste text**; the extracted text can be checked and edited before saving; the name defaults to the file name (e-mail subject) or the first line of the text. Adding only saves the source – **Process** (button in the source detail, "Process again" later) sends its text to the AI, which proposes new records and additions to existing ones exactly like the former notebook processing (verbatim quotes from the source, merge of additions, three-column review); every confirmed record (created or updated) gets a connection to the source, and the source gets its processing date even when every proposal was skipped. Sources appear on the project detail in the Basic information column (a card with the count, not among the artifacts), on the canvas (card text = beginning of the source text), in the document, search, export/import, change history and the data folder (`sources/`). Notebook messages of the former "Enter information" mode (and the old plain-text notebook) are converted to sources (kind "other", processed when the message had been processed) on the first start; questions stay in the chat.
**Risks** - code (RSK-…), name, description, likelihood (high/medium/low, shown as Vysoká / Střední / Nízká), impact (high/medium/low, shown as Velký / Střední / Malý), mitigation, status (open/mitigated/occurred/closed). Typically captured at the kick-off or a pre-mortem. Not synchronised to the Flexi API (no server collection).

**Activities** - configurable task templates with checklists & deadlines. The built-in catalogue (31 techniques grouped as project / UX research / UX design: kick-off, deep dive, pre-mortem, desk research, stakeholder interviews and map, competitive and heuristic analysis, content audit, screener, interviews, survey, behavioural segmentation, personas, value proposition canvas, top tasks, journey mapping, requirements, context scenarios, prioritisation workshop, card sorting, information architecture, tree testing, design studio, low-fi prototyping, wireframing, usability testing, functional specification, handoff, retrospective) is distilled from the design team's internal technique library; every type carries a methodology (why, when, duration, who, steps, outputs) shown on the activity detail: the detail has up to three columns in the 12-column layout grid (default: left 4, checklist 4, right 4 columns; without a checklist left 8, right 4), each column framed as a card – left: status and deadline at the top, then the type description with why / when / duration / who and the notes; middle: the checklist; right (always present): the "How to" box with steps and outputs (collapsed when the detail opens) and below it the "Meeting notes" box. Meeting notes: the user loads a transcript from a file (the same formats as sources: Word, PDF, text, e-mail; drag & drop or a button; the extracted text appears in the field and can be edited) or writes / dictates the notes into the text field, then "Save and process" (just "Save notes" without AI). Saving creates a source of kind "Meeting notes" (code ZDR-…, name from the file or "Meeting notes – <activity> – <date>") connected to the activity in one change, so it immediately appears in the activity's Connections, and starts its AI processing right away – the same review of proposals as for any source (confirmed records get connected to the source, the source gets its processed date). The box shows the state of the last saved notes (processing / waiting for confirmation / processed / nothing found / error) with a link to the source. The checklist column is left out when there is no checklist; at medium width the third column moves below the first two, in a narrow space (e.g. a canvas window) everything stacks. The connections are below the columns across the full width. Only the original 13 types are created automatically for a new project (configurable per template). Each checklist follows the “How to” steps in the same order (every item is a verifiable outcome of a step). Checklist item ids of existing types never change, so stored activities keep their progress (an activity keeps the checklist it was created with); each checklist item may spawn a linked **Task** (the checklist row remains); the new task is automatically added as a connection to the activity (`checklistItemTaskIds` maps checklist item id → task id). **Assign task** (UI: „Zadat úkol“) from an activity (project list or activity header) opens the same **Add task** dialog as the Tasks section, with the task **name prefilled from the activity name**; on Save the task is created and linked only via **EntityConnections** (no checklist item link). Creating from a **checklist row** still uses the same Add task dialog with the step label as the prefilled name and keeps the checklist item link. Opening an already linked checklist task goes to the task detail page.

**Tasks** - SMART goals with due dates & assignees

**Bugs** - issue tracking with severity/impact/priority

**Team Members** - project team roster with roles



### Relationships (many-to-many, no cascading deletion)
 Arbitrary connections between any entities via `EntityConnections`. The connections panel **hides** rows where the linked entity was deleted (no placeholder row); orphan records may still exist in stored data until manually pruned or a future cleanup.

Legacy fields `_ts` and `_uxlog_id`, written into records by an older version of the Flexi API sync, are removed from all records when the data loads (the current sync keeps its timestamps and id mapping outside the records), and the local HTTP API does not store them either. When two records with the same id meet (deduplication), the one with the later `updatedAt` (then `lastWorkedAt`, `createdAt`) wins.

### Data folder (vault) – project data as files
The project data as a folder of plain files (the "vault"), so external tools such as Claude Code can read and edit it. The app writes the files, and changes made in the files come back into the app automatically (always; only conflicts and unusually large batches wait for the user). When the folder is on, it is the source of truth and the app database (SQLite) is only a cache that can always be rebuilt from it. 

Folder as the source of truth: every write gives the manifest (`.uxlog/manifest.json`) a new random sync mark (`syncId`), and the database remembers the mark it wrote last, together with the folder path (`uxlog_vault_sync`). Before every write/check the two marks are compared:
- same mark → the database matches the folder (it may only hold newer edits that were not written yet) → the normal write and automatic loading follow;
- the folder has no project yet (new or emptied folder) → the app data are written into it; stale manifest entries of project files are dropped first, so the missing files are not taken as deleted;
- an older installation without marks on either side, with data in the database → it continues as before and the mark is added by the next write;
- anything else (the folder was written by another computer, the database was restored from a backup or is empty, a different folder was chosen) → the database is rebuilt from the folder before anything is written: the folder wins, records missing in the folder are deleted, new ones added; a record without id gets one, a record without code gets the next free code; a file with errors never deletes its record (the database version is kept, for a broken `project.md` the whole project); the canvas layout and the notebook chat history are kept from the database only when the folder has none; record order follows the database. The rebuild is one history entry per project ("From the data folder", revertible), a toast reports the number of changed records, and the loaded files are accepted into the manifest. While the user is typing in a field, the rebuild (and with it the write) is postponed by a few seconds.

Settings (the "Data folder" card on Configuration → Connectors, first, above the plugins, with a hint that each project can choose its own folder, desktop app only; enabled folder counts as a configured connector; stored under `uxlog_vault`): an on/off switch and the folder, chosen with the system folder picker. The default folder is Documents/UXLog/Data, and "Open folder" shows it in the file manager.

Per-project folder (project detail → menu ⋮ → "Data folder…", shown only while the data folder is on; the setting belongs to this computer only and is stored in `uxlog_vault.projects`, never in the project data): "Default data folder" (no entry), "Own folder" (`{ root }`) or "Nowhere" (`{ off: true }`). A project with its own folder is written directly into that folder's root – `project.md`, `connections.yaml`, `INDEX.md` and one subfolder per record type – together with its own `.uxlog/` (manifest, base, sync mark, canvas, notebook, CLI; `workspace.yaml` carries `layout: project`), `.claude/` and `CLAUDE.md`; any other content of the folder (e.g. the project's source code) is never read, written or deleted. The own folder must not be the default folder, lie inside it or contain it, and two projects cannot share or nest folders – such a choice is refused in the dialog; a stored invalid setting means the project is not written anywhere and the problem is shown. If the chosen folder already contains a different project (`project.md` with another id or without id), nothing is written to or loaded from it and the dialog and the Connectors card say so. Changing the folder moves the project: the files the app wrote to the previous own folder (unchanged since) are deleted together with its manifest and base (files edited outside the app and `CLAUDE.md` stay), a project leaving the default folder disappears from it the same way, and the project is written to the new place. "Nowhere" removes the project's files the same way and stops writing and loading it. The Connectors card lists projects with their own setting (folder or "not written") and any folder problems. Every folder is checked, rebuilt (only its own projects – other projects and their copies in that folder are ignored), written and loaded separately with its own sync mark (`uxlog_vault_sync` keeps one mark per folder) and its own watcher; lists of changes, conflicts and files with errors show the file path on disk, prefixed with the folder name for own folders. When the switch is on, the app writes the files on startup, about 1.5 s after the last saved change, after changes coming through the local HTTP API, shortly after the app window regains focus (e.g. after returning from Claude Code), and about 1.5 s after the last change of a file in `projects/` made outside the app (the folder is watched while the app runs; a burst of changes means one check, and the app's own writes cause only a check that finds nothing). File operations never run concurrently. It writes only files whose content changed, deletes the files of deleted records, and moves files when a record or project is renamed. Only the `projects/`, `.uxlog/` and `.claude/` subfolders and the root `CLAUDE.md` are touched, and only `.md`/`.yaml`/`.json`/`.mjs` files. Every write is atomic (temporary file + rename). The app remembers the SHA-256 hash of every file it wrote in `.uxlog/manifest.json`. A file whose current content differs from what the app wrote (edited outside the app), a file the app did not create at a path it wants to write, a file the app wrote that was deleted outside the app, and a new data file in `projects/` that the app never wrote are never overwritten, recreated or deleted. They are listed in the "Changes in files" card under the settings, each with its reason (modified outside the app / not created by the app / record no longer exists but the file was modified / deleted outside the app / new file). Any of them except new files can be overwritten with the app version after a confirmation, one by one or all at once.

Loading changes (files → app): "Review and load changes…" (shown when some change concerns `projects/`) opens a preview. It lists every change with Load / Skip and offers "Load all":
- a new file is a new record (a missing id is generated, a missing code gets the next free code in the project, the project comes from the folder), and a new `project.md` is a new project;
- an edited file is an update showing only the changed fields, before → after (timestamps ignored; fields missing in the stored record are compared with the entity defaults);
- a deleted file is a deletion of the record, done like a deletion in the app, including removal of links and the canvas card;
- a file moved to another project's folder changes the record's project (the old path does not delete it);
- an edited `connections.yaml` replaces the project's connections (added / removed / changed);
- a deleted `project.md` cannot be loaded (deleting a project only in the app).

Files with errors are listed with their problems and are not loaded. Files that were only reformatted are accepted automatically. All loaded changes of one action form one entry in the project change history and can be reverted. After loading, the files are accepted (their current hash goes to the manifest), and the next write rewrites them into the canonical form and file names. A skipped change stays in "Changes in files" and its file is not overwritten.

Automatic loading (always on, there is no switch): after every write/check the changes in `projects/` are loaded without asking – new, edited and deleted records alike (a deleted file deletes its record). Edits are merged three-way per field against the base (`.uxlog/base.json`, the record as it was when the app and the file last agreed): a field changed only in the file is taken from the file, a field changed only in the app is kept, link lists (`*Ids`) changed on both sides are merged as sets, and a field changed differently on both sides is a conflict. Without a base the file wins. Non-conflicting fields of a conflicting record are loaded right away; the conflicts wait (status bar "n conflicts", a toast, and "Resolve conflicts…" in a card under the settings) and the user chooses the app or the file version per field in three columns (in the app / originally / in the file); until then the file is not accepted and not overwritten. Safety limits (`vaultAutoImport` in `data/app.yaml`): an unusually large batch (more deleted files than `maxDeletes`, or more than `maxShare` of a project's records changed at once once there are at least `minChanges` changes) and a deleted `project.md` are never loaded automatically – they are only offered in the manual preview. While the user is typing in a field in the app, loading is postponed by a few seconds. Automatically loaded changes are one history entry per batch and can be reverted.

Files for Claude Code (written together with the data): `CLAUDE.md` in the root (created only when missing, the user may edit it; it imports the rules), `.uxlog/claude/RULES.md` (format and working rules, template `data/vault/RULES.md`), skills `.claude/skills/uxlog-data`, `uxlog-edit-entity`, `uxlog-research-synthesis` and `uxlog-review` (templates `data/vault/skills/*.md`), `.claude/settings.json` and the CLI `.uxlog/bin/uxlog.mjs`, which needs Node.js.

The settings file contains hooks that run the CLI:
- before every Edit/Write the hook blocks changes to `.uxlog/`, `.claude/settings.json` and `.claude/skills/uxlog-*`;
- after every Edit/Write of a file in `projects/` the hook checks the whole folder. Errors in that file block with feedback to Claude, warnings are passed to Claude as context.

The settings file also contains deny rules for `.uxlog/`. The user's own Claude Code settings belong in `.claude/settings.local.json`.

CLI commands:
- `validate [paths] [--json]` – errors fail with exit 1;
- `schema [type]` – sections, front matter fields, allowed values, links, completeness fields;
- `list [type] [--project]`;
- `new <type> --project P --name N [--set field=value]` – correct id, next code, defaults; `new project --name N`;
- `link`/`unlink <record> <field> <target…>` – link fields of the same project and the right type;
- `delete <record>` – deletes the file and removes links to it from other files and from `connections.yaml`;
- `hook`.

A record is given by path, id or code, a project by folder name, name or id. A change that would introduce an error or a link to a non-existing record is not written.

Folder checks:
- errors: unreadable file, duplicate id, a value not allowed for a select field, duplicate code in a project, a link field that is not a list, an unknown record type in a connection, a project folder without `project.md`;
- warnings: missing id or name, code not matching the type prefix, a link to a non-existing record (tolerated, older data contain them), duplicate link, unknown file.

Each project folder also has a generated `INDEX.md` (code | name | file | id per record type), which is ignored when reading. The screen shows the last write (time, number of files, written, deleted), file errors and the number of records that belong to no existing project (they are not written). The status bar shows "Data folder" with the time of the last write while the export is on.

File format: Layout: `.uxlog/workspace.yaml` (`formatVersion`), `.uxlog/canvas/<projectId>.yaml` (canvas layout, machine-managed), `.uxlog/notebook/<projectId>.yaml` (notebook chat history `notebookHistory`, machine-managed, written only when not empty), and `projects/<project name>/`. The project folder has the project name as it is (characters forbidden on Windows replaced, Unicode NFC, a ` (2)` suffix on collision for the newer project). Inside it: `project.md`, `connections.yaml` (only when the project has connections) and one subfolder per record type (`goals`, `stakeholders`, `competitions`, `hypotheses`, `personas`, `scenarios`, `requirements`, `risks`, `activities`, `team`, `tasks`, `bugs`), each holding one `<CODE>-<slug>.md` per record (`-2` suffix on collision). A record file has a YAML front matter (id, code, select/number values, relation id lists annotated with `# CODE name` comments, custom fields, timestamps), then the name as `# H1`, then every long text attribute as a `## <attribute label>` section. A text that would not read back unchanged as a section (it contains H1/H2 lines outside code blocks, an unclosed code block, leading blank lines, trailing spaces or CR) stays in the front matter, so the round trip is always lossless. When reading: identity comes from `id`, not from file or folder names; section headings match the label or the field key regardless of case and diacritics; a non-empty section wins over the same key in the front matter; unknown sections and text before the first section are kept as `extraSections`; missing fields are filled from the entity defaults; `projectId` comes from the folder. `project.md` has the project name as H1 and the notebook as its body; the notebook chat history and the canvas are not part of it. A broken file (YAML syntax error, unterminated front matter, front matter that is not a map, duplicate key) is reported and skipped while the other files load; duplicate ids are reported and only the first file (by path) is loaded; a project folder without `project.md` is reported and its records are skipped; a record without `id` is loaded with a warning.



Appearance: the status bar has a "Vzhled" selector (right end) with five looks, stored per computer (`uxlog_theme`): **Moderní** (default modern dark look); **Amiga** – an Amiga Workbench 1.3 screen: four colours (blue background, white, black, orange accent), a pixel font, no rounded corners or animations, bevelled "gadget" buttons, windows (cards, dialogs) with a white frame, black drop shadow and a title bar with a close gadget and stripes, a white screen title bar with depth gadgets, a red pixel mouse pointer; **macOS** – a light, airy modern desktop look: system font, rounded corners, soft shadows, translucent blurred top and status bars, a segmented Data / Canvas / Document switch, blue gradient primary buttons, pill badges, focus rings, dialogs with three "traffic light" dots, thin scrollbars; **PixelArt** – 8-bit game graphics: a pixel font with Czech diacritics, a limited saturated palette on a dark navy pixel-grid background, stepped pixel frames with cut corners, buttons that sink when pressed, yellow headings with a hard shadow, a pixel mouse pointer; **Sci-fi** – a futuristic HUD: near-black background with a teal glow from the top and a fine grid, translucent teal panels with a thin glowing cyan frame, chamfered top-right and bottom-left corners, thicker accent segments and small slanted dashes on the edges, chamfered glowing buttons, technical uppercase headings (Rajdhani / Exo 2). The chamfers are drawn as overlays, not by clipping, so menus inside cards stay visible.

## Plugin System
Event-driven plugin registrywith capabilities and event bus.
       
       
**Built-in plugins:**

**data-status** - tracks last sync timestamp

 **tauri-local-api** - HTTP API server on 127.0.0.1:17842 (desktop <-> Figma communication). Every request except the CORS preflight must carry a `Host` header of `127.0.0.1:17842` or `localhost:17842` (otherwise 403) and `Authorization: Bearer <key>` matching one of the API keys created in the app (otherwise 401); with no keys the API admits nobody. Keys are managed on the card "Local API – Figma plugin" on Configuration → Connectors (desktop only): the card shows the API address and the list of keys (name, visible start of the key, creation date, last use since the app started) with "Revoke" (after a confirmation; the key stops working immediately). "Create key" (optional name, default "Key N") generates a random 256-bit key `uxlog_` + 64 hex characters and shows it once with "Copy key" – the app stores only its SHA-256 hash with the name, visible start and creation date (`uxlog_local_api_keys`, this computer only, never exported or written to the data folder), so the key cannot be shown again. Records written through the API reach the open app record by record: the backend numbers every write (revision) and keeps the written record in memory (the last 1000 writes); the app asks for the writes newer than the last revision it has seen (immediately after each write is announced and every 2.5 s as a fallback) and merges only those records into its data – only the fields that were sent are merged into the current record (other fields stay as they are in the app), changes of records the app does not have and changes that do not alter anything are skipped. A write through the API (`PUT`) only edits an existing record (otherwise 404): the sent fields are merged into the stored record, while `id`, `projectId` and `createdAt` cannot be changed. The Figma plugin sends only the fields changed on the card, so fields the card does not show or did not change are never overwritten with an older copy. The merge is saved as a change made outside the app (it appears in the project history and can be reverted), and a write cannot be lost even if the app saved its own data in the meantime. Only when the backend no longer has the requested writes is the whole database reloaded.
       
**flexi** - optional sync to Flexi API backend

AI requests (OpenAI, Gemini) have a time limit (`ai.requestTimeoutMs` in `data/app.yaml`, default 120 s, at least 5 s); a request that does not answer in time ends with a message saying so. Every "AI is working…" indicator (Chat message, source processing, meeting notes, connection suggestions, competition analysis) has a "Cancel" button that cancels all running AI requests; the place then shows that the request was cancelled (in the Chat with "Try again"). A long text processed in parts stops at once when cancelled, and a part that timed out is not retried. The Gemini API key is sent in a request header, not in the URL.

**openai** - ChatGPT integration (notebook processing `ai:notebook`, merging new information into an existing record `ai:merge`, notebook questions `ai:ask`, connection suggestions)

**gemini** - Google Gemini AI (same capabilities as OpenAI)

**recognita** - dictation by voice through the user's own Recognita speech-to-text server (desktop app only; capabilities `dictation:start`, `dictation:test`). Settings (card "Recognita – dictation" on Configuration → Connectors, shown while the plugin is on; stored only on this computer under `uxlog_recognita`, never exported): server address (base URL; a pasted `/api/…` path is stripped, `https://` is added when missing), API key (shown masked), language (default `cs`, empty = automatic detection), specialist terms (sent as `initial_prompt` to improve accuracy) and an on/off switch; "Test connection" connects, waits for the server's `ready` and ends the session, reporting success or the reason of failure. While the plugin is on and the connector is configured, every multi-line text field (forms, inline editing of long texts in details, connection notes, activity template description, the Chat input) and every single-line plain-text field (names, short text attributes in forms and details; not e-mail, URL, phone, number or date fields, and not search or configuration fields) shows a microphone button in its corner (at the right end of a single-line field). Pressing it starts live transcription: the microphone audio is converted to 16 kHz mono 16-bit PCM and streamed in 250 ms blocks over a WebSocket (`/api/v1/stream`, API key in the `Authorization` header – the connection is held by the desktop backend because a browser WebSocket cannot send that header); the text appears at the cursor position (replacing a selection) as it is recognised – the confirmed part plus the provisional ending, which may still change – with spaces added at the joins. The field is read-only while dictating. Pressing the button again (stop) ends recording; the server finishes the transcription and its final text replaces the live text. Only one dictation runs at a time (also a server limit – another live transcription on the server is reported as "busy"). Resilience: the connection must be established within a time limit; the backend pings the server every 5 s; a server silent for longer than `slowAfterMs` shows "server responds slowly" while dictation continues, silent for longer than `stallAfterMs` ends dictation as an outage; after stopping, the app waits at most `finishTimeoutMs` for the final text and otherwise keeps the live text with a warning that the end may be incomplete (limits in `data/app.yaml` → `dictation`). Any failure (server unreachable, invalid key, busy, connection lost, microphone denied) is shown under the field with a specific message and "Try again"; the text dictated so far always stays in the field and a retry continues after it. Leaving the screen or closing the editor ends the connection and keeps the text.

**ai-shared** - shared AI utilities (key management, prompts)


## Key Features
Entity list + detail on one screen: every entity section (goals, risks, hypotheses, competition, requirements, personas, scenarios, bugs, sources, tasks, team, stakeholders) shows its list on the left (4 of the 12 grid columns; filters, search and "Add" stay there; list items show only the title and tags, no description text) and the detail of the selected item on the right (8 columns): the detail itself framed as a card, its Connections below the frame. The URL of a detail stays the same as before (`/project/:id/<section>/<itemId>`); without a selection the right side shows a hint to pick an item. The selected item is highlighted in the list; list cards have no "…" menu (move, copy, delete and change type are in the detail's "…" menu); the list has no scrollbar of its own – it is shown in full and scrolls with the page, while the detail stays in view (a detail taller than the window first scrolls until its bottom is visible, then stays put). The screen header then shows the detail's breadcrumbs (… / section / item) and actions; without a selection it shows the list's header (import / export of the section). In a narrow window only the list is shown, and after picking an item only the detail (back via the breadcrumbs). Activities keep their own detail screen (opened from the project detail).

Project screens layout: every screen inside a project (project detail, activity detail, artifact lists and artifact details) starts with a full-width header – project colour, breadcrumb navigation (no large page title; breadcrumb items are links only, the project is edited from the menu), screen actions (Import, Export, menu) aligned right. Project metadata (priority, scope, last activity) is shown only in the project list. Below it the selected screen. The layout is at most 1500 px wide and every screen with columns uses one standard 12-column grid with a common gap (column widths per screen are set in one place and can be tuned); by default the project detail gives 7 columns to three content columns – **Basic information** (Tasks, Sources, Team, Stakeholders; more will follow), **Activities** and **Artifacts** (in this order: goals & metrics, risks, hypotheses, competition, requirements, personas, scenarios, bugs) (2, 3 and 2 grid columns) – and the remaining 5 to the **Chat** (sticky while scrolling, unsent draft kept when navigating within the project); on narrower windows the three columns become two, then one. For now the Notebook is shown only on the project detail – every other project screen uses the full width. On narrow screens the chat moves below the content. The content column starts with a column heading styled like "Notebook": entity lists show the plural section name (e.g. "Personas") with the add button aligned right; entity and activity details show "<type> <name>" (e.g. "Persona Jana"; activities "Activity: <name>") – clicking the heading (pencil on hover) renames the entity – with the editable code below it where the entity has one (stakeholders show their strategy badge there).
Chat (formerly Notebook; panel on the project detail; requires AI): the user sends a text message (Ctrl+Enter); every message is kept permanently in the project's chat history (`notebookHistory`, no editing or deletion). A select left of the send button switches between two modes: **Change data** (button "Propose changes") – the message is an instruction (e.g. "create a persona from the interview with Jana"); the AI gets the project's records and the text of its sources and proposes create/update actions that fulfil the instruction, reviewed in the same dialog as below (quotes are checked against the instruction and the sources). **Ask** (button "Send question") – AI only answers in text using the project's data (all entities incl. activities, tasks, bugs, their custom fields, and for every item its connections from **EntityConnections** – items without connections are explicitly marked as having none; legacy ID-list fields such as `scenarioIds` are not used) the text of the project's sources (newest first, shortened, cited by code or name) and earlier chat messages; it never writes to entities or anywhere else (only the question and answer are kept in the history); requires AI. The former **Enter information** mode (processing a pasted text) is now done by Sources. If AI is available, the message is processed and the proposed create/update actions are reviewed in a dialog (confirm / skip each, or all); actions left unconfirmed when the dialog closes count as skipped. The AI reply under the message summarises the outcome (written / skipped per entity). Long messages and replies are shortened to a few lines; clicking them (or "Show all") expands them. The history scrolls without a visible scrollbar and stays at the newest message. Messages of any length can be processed: long text is sent to the AI in parts (by paragraphs, ~6000 characters each) and the proposals are merged (the same record from several parts becomes one action); the AI is asked for a JSON response with verbatim source quotes only, a truncated response still yields all complete actions, a failed part is retried once and, if it still fails, the message shows which share of the notes was not processed. Without AI the message is just saved. Failed or interrupted processing can be retried. Adding information to existing records: the AI sees every existing record with a shortened summary of its main fields (personas: description, context, needs, problems) and is told to propose an update when the notes talk about the same entity as an existing record, even under another name or from another point of view, and to create a new record for every new entity – similarity (same area, related topic, similar role) is not identity, and when unsure it creates a new record, which the user can still merge in the review. For each proposal it returns 1–5 verbatim excerpts of the notes it is based on; the app checks every excerpt against the notes (differences in whitespace and line breaks are tolerated and replaced by the exact source text, quotation marks added around an excerpt are removed) and marks excerpts not found verbatim. For an update the app makes a second AI call with the record's complete current values and the excerpts, and the AI returns the full merged wording of the changed fields (existing content kept, new information worked in, contradictions kept side by side, direct quotations copied character by character). The review shows each proposal in three columns: **Current record** (read-only, changed fields highlighted) | **From the new text** (the excerpts; unverified ones with a warning) | **Proposal** (editable; changed fields on top, the record's other fields collapsed under "Other fields without change"). A direct quotation in the proposal (text in quotation marks or the whole "quote" field) that is not found verbatim in the notes or in the original record gets a warning. While the merge is running the proposal cannot be confirmed ("Accept all" confirms only finished ones). If the AI merge fails, the new information is appended to the end of the existing text (sentences already present are skipped) and the proposal says so with a "Try again" button. "Save as" above the columns switches a proposal between "New record" and "Add to: <existing record of the same type>" (the latter starts the merge). Every new record must have a name: the AI is required to fill it and to derive a short name from the record's content when the notes don't name it; if it still comes back empty, the app uses the proposal's label or derives the name from the first sentence of the record's text (shortened at a word boundary to about 60 characters). The name is always the first field of a new record's proposal; a proposal without a name cannot be confirmed (warning at the field), and a merge never clears an existing record's name. Confirming an update writes only the fields that differ from the record as it was when the review started; an update of a record that no longer exists becomes a new record. All AI outputs (proposed field values, answers, connection notes, competitor descriptions) are written in the language the user wrote in (notes, question, topic or entity texts); they are never translated to English – only JSON keys and enum values stay in English. Czech is detected by its diacritics and named explicitly in the prompt; otherwise the AI is told to keep the user's language.
Project list: projects are shown as tiles (without a coloured side stripe; the project colour is the square before the name) in the 12-column grid, by default 3 grid columns per tile = four per row on a wide screen (three, two and one on narrower ones), tiles in a row have the same height. Order: projects the user has not moved yet (no `sortOrder`, or the factory default 9999) come first, newest first (by creation date) – so a new project appears at the start; after them the order the user set by dragging tiles (drag & drop, saved as `sortOrder`). There is no project deadline (the concept was removed; a `deadline` stored on a project by an older version is dropped when the data are loaded, together with the old default project durations in the configuration). Activities keep their own deadlines. Project list: compact tasks-count tag links to the project’s Tasks section (if any tasks are overdue, URL may include `?overdue=1` to turn on the overdue filter). Tasks list: **by default the “incomplete” filter is on** (only incomplete tasks); **filter and search text persist in memory per project for the browser tab session**, so returning from a task detail restores the same filters. Incomplete overdue items are visually emphasized; “Prošlé” filter matches any task whose due date is in the past. Multi-select list filters (tasks, bugs, requirements, personas, hypotheses, scenarios) use **OR**: an item appears if it matches **at least one** active badge.
Activity recommendations: the Activities panel suggests up to three techniques the project does not have yet (incl. removed ones), based on the state of artifacts – no risks → pre-mortem, no or incomplete stakeholders → stakeholder analysis, no competitors → competitive analysis, no personas → personas, personas without a connected scenario → scenarios, uncategorised requirements → requirements, five or more requirements with identical priority → prioritisation workshop, untested hypotheses → usability testing. Each suggestion shows its reason and an Add button.
AI methodology: notebook processing prompts follow the technique library rules (requirements as needs not solutions with a category, hypotheses as "I think that … because …", scenarios with trigger and outcome, stakeholder attitude, direct/indirect competitor, risk mitigation). In Ask mode the methodology of the project's activities is added to the context so the AI can answer how-to questions.
Change entity type: goals, stakeholders, competition, hypotheses, risks, personas, scenarios, requirements, tasks and bugs (types marked `convertible` in the entity configuration) can be turned into another of these types from the detail's "…" menu ("Change type"). A dialog compares the original record (left) with an editable proposal of the new record (right) row by row: the same field of both types (name, code, fields with the same key, custom fields with the same label) is on one row, original fields without a counterpart come last, and a value that goes to a different field is labelled with it; only the comparison scrolls, the buttons stay below it; changing the target type rebuilds the proposal. The proposal copies the name, fields with the same key and a compatible type (a select value only if the target offers it; custom fields are matched by label) and gets a new code with the target prefix; fields without a target are appended to the target's main text field (description, else its first multi-line field) as "Label: value", so nothing is lost; other fields start with the target type's defaults. Confirming creates the new record, re-points the original's connections to it (dropping duplicates and self-links), keeps its canvas position and colour, deletes the original (its legacy links are cleaned like on any delete) and opens the new record's detail (in a canvas window: a new window replaces the old one). It is one history entry and can be reverted. Activities, sources and team members cannot change type.

Project change history: every user change in a project (create, edit, delete of any record incl. connections, reordering, moves between projects, imports and confirmed AI proposals) is recorded per project – one history entry per user action (all changes made by that action together), with the full before/after state of each affected record. Automatic fields (`updatedAt`, `lastWorkedAt`), the notebook chat history and the canvas layout are not recorded; changes coming from sync are not recorded. The "History" screen (link in the header of every project screen) lists entries newest first with a summary, the changed fields and a "Revert" button. Reverting applies the inverse changes to the current state (created records are removed, deleted records come back, edited fields get their previous values while later edits of other fields are kept) and is itself recorded as a new entry, so a revert can be reverted again; the reverted entry is marked as reverted. History keeps the last 100 entries per project and is stored separately from the app data (key `uxlog_history`, mirrored to the desktop storage). A deleted project keeps its history; the project list shows "Deleted projects" with a "Restore" button that brings the project back with all its records, and a "Delete" button that – after a confirmation – removes the project permanently (its history, from which it could be restored, is discarded; this cannot be undone).
Export files: in the desktop app a downloaded export is saved to Documents/UXLog and shown selected in the system file manager (PDF is opened in the default viewer); a toast shows the full path, or the reason when saving failed. Copying to the clipboard confirms with a toast. The export YAML quotes map keys that are not simple identifiers; the importer also reads older exports where such keys (e.g. `personas:<id>`) were written unquoted.

Project views: inside a project the app header shows a three-button switch right of the "UXLog" logo – **Data** (the screens with entities and the Notebook; it returns to the last data screen visited in that project, the project detail by default), **Canvas** and **Document**. Project document: the whole project data rendered as one readable document that fills the window below the app header (no screen header or Notebook): the project name as the main heading with scope, priority and phase below it (read-only), then one section per artifact type – only the types of the Artifacts column of the project detail, in the same order (goals & metrics, risks, hypotheses, competition, requirements, personas, scenarios, bugs; sources, tasks, team, stakeholders and activities are not part of the document; empty sections are left out) with a table of contents on wide screens, every record as a sub-heading (code links to its detail in Data) followed by its short attributes as a property list (select, text, date, number with unit) and its long text attributes as a small heading + paragraph; attributes follow the entity attribute configuration (hidden, custom and conditional attributes included). Empty attributes are hidden unless "Show empty fields" is on. Editing happens directly in the text: the project name, record names, text attributes and paragraphs are editable in place (plain text; Enter confirms a one-line field, Enter adds a line break in a paragraph and Ctrl+Enter confirms, Esc reverts); a change is saved when the field is left – into the record itself, exactly like an edit in the detail (change history, last-worked date); an empty name is not saved and leaving a field without a change saves nothing. Select, date and unit attributes are edited with an inline picker. Search: a search box in the document toolbar (Ctrl+F) finds every occurrence in the document regardless of letter case and diacritics, highlights all of them, marks the current one, shows "current / total" and moves between them with Enter / Shift+Enter or the arrows. Export: "Export to Markdown" copies the document to the clipboard or downloads it as a `.md` file (# project, ## section, ### record, short attributes as a "**Label:** value" list, long attributes as #### heading + paragraph; empty attributes left out; record texts are written as they are, so Markdown in them is kept). The document itself is never stored – it is always derived from the data. Project canvas: a Miro-like infinite board of the project that fills the whole window below the app header (no screen header, breadcrumbs or Notebook – an unsent Notebook draft is kept for the return). Floating controls: a type filter centred on the top edge ("Highlight": "All types" plus every card type with its number of cards in the project, types without cards are disabled) – choosing a type makes all cards of other types nearly transparent (15 % opacity) so the chosen type stands out (only the look changes: dimmed cards can still be selected, moved and opened; the filter is not saved and resets when switching projects); a one-line control legend in the bottom-left corner; selection count, zoom −/+ with the zoom level and "Fit all" in the bottom-right corner. The default view and "Fit all" keep the strip under the filter free of cards. Frames: the "Frame" tool in the top-left corner (shortcut F, Esc cancels) lets the user draw a rectangle on the board (a click without dragging inserts a 520 × 320 frame; minimum 160 × 120); a new frame gets the title "Frame n" and immediately offers renaming. A frame is a titled area behind the cards; its title sits above its top edge. A card belongs to a frame when the card's centre lies inside it, so a card is put into a frame simply by dragging it there; frames don't store their cards. Dragging the title moves the frame together with its cards and with frames lying completely inside it (one save on release); clicking the title selects the frame (card selection is cleared), double-click or F2 renames it (an empty title is not saved), the corner handle of a selected frame resizes it. The frame body does not react to the pointer, so selection rectangles, panning and card dragging work inside frames. A selected frame shows the same floating toolbar as cards: frame color (tinted background and colored border, palette shared with cards) and a menu with "Rename" and "Delete frame" (Delete key works too); deleting asks for confirmation and never deletes the cards. Smaller frames are drawn above bigger ones. "Fit all" includes frames. Frames are part of the canvas layout: not recorded in the change history, no change of the last-worked date, not part of export/import. Every project record (goals, stakeholders, team members, competitors, hypotheses, personas, scenarios, requirements, risks, activities except removed ones, tasks, bugs) appears as a square card with its type, code, a priority tag at the right end of that row (requirements and scenarios: MoSCoW, shown short as Must / Should / Could / Won't, missing = Could; bugs: the priority computed from severity and impact, only when both are set; colored by level: must/critical red, should/high orange, could/medium yellow, won't/low grey), name (long names wrap to several lines, never truncated) and the beginning of its description filling the rest of the card (fading out where it does not fit). A card without a saved position is placed in its type's column (one column per type present in the project, cards stacked in list order). Selection: clicking a card selects it (Shift/Ctrl+click adds or removes it), dragging on empty space draws a selection rectangle that selects every card it touches (with Shift/Ctrl it adds to the selection), clicking empty space or Esc clears the selection, Ctrl+A selects all; selected cards are highlighted. Selection toolbar: while one or more cards are selected, a small floating toolbar is shown centred above the selection (below it when there is no room above without covering the type filter, just under the filter when there is room neither above nor below); it follows panning and zooming and hides while cards are dragged or a selection rectangle is drawn. It has two tools: **Card color** – a palette (configurable in `data/app.yaml`, `canvasCardColors`) plus "No color"; the chosen color becomes the card background and the text color switches automatically between dark and white, whichever has the higher contrast (WCAG), secondary text and border are derived from it; the button shows the selection's common color, or a multicolor swatch when the selected cards differ. Card color is a canvas-only property of the project's layout (not of the record), is not recorded in the change history and does not change the last-worked date. **Actions menu (…)** – the same actions as the record detail: "Move to another project", "Copy to another project" (the same project picker dialog, applied to all selected records) and delete (with the record's own label and confirmation for one card, "Delete selected (n)" with a count confirmation for more); deleting several records is one history entry that can be reverted. Moving a record to another project drops its canvas position and color in the source project. Moving: dragging a card moves it, dragging a selected card moves the whole selection; the arrow keys move the focused card or the selection (Shift for a bigger step). Positions are saved when the drag ends and kept. Panning: right or middle mouse button drag, or Space + drag; the mouse wheel zooms around the cursor (20–250 %), the floating buttons zoom in/out and "Fit all" shows every card; the last pan/zoom is remembered per project. Double-clicking a card (or Enter on a focused card) opens the record's detail in a floating window over the board – the user stays on the canvas and the board remains usable. Every opened record gets its own window (opening an already open record only brings its window to the front); new windows appear near the top-right corner, each next one cascaded down-left so it never exactly covers another. A window (default 560 × 480 px, smaller on a small screen) can be moved by dragging its title bar and resized by dragging its bottom-right corner (minimum 360 × 240 px; its title bar always stays on the board); clicking a window brings it to the front. The window shows the full detail with all its editing, connections and actions except import and export (move/copy, delete); deleting or moving the record away closes its window, a link to a connected record opens that record in another window. The title bar shows type, code and name, the record's actions menu and Close; Esc closes the focused window. Windows are not saved – leaving the canvas closes them; windows of records deleted elsewhere disappear. Moving cards and the board does not change the project's last-worked date and is not recorded in the change history; positions of deleted records are dropped. Canvas layout travels inside the exported project record (map keys such as `personas:<id>` are written quoted), but import ignores it.

Configuration per project: the configuration (activity templates, custom entity fields and overrides of built-in fields) exists as a **default configuration** and as a **project configuration**. The default configuration (header "Configuration" outside a project, screen "Default configuration" with a hint) is only the template for new projects; it also holds the Connectors, which are shared by all projects. Every project has its own copy (`project.config`), created when the project is created (from the default configuration at that moment; projects from older versions get a copy of the default configuration on the first start, records loaded from the data folder or an import without one get it on the next save). Changing a project's configuration never affects other projects or the default configuration, and changing the default configuration never affects existing projects. Inside a project the header button "Configuration" opens "Project configuration" (`/project/:id/config/…`, the same screens as the default configuration: entities and their attributes, activity templates, plus the project's data folder); everything inside the project – entity details and forms, custom fields, activities and their checklists, recommendations, the document, the Notebook AI and the delay check on the project list – uses the project's configuration. The project configuration travels with the project in export/import and in the data folder (`.uxlog/config/<projectId>.yaml`, app-managed), is not recorded in the change history and does not change the last-worked date. On the project list the header button "Projects" is hidden (it would lead to the same screen).
