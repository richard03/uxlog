**UXLog** is a desktop application for UX design process logging and cooperation with Figma. It operates in a closed environment without internet connection; plugins may add connections such as LLM services or external APIs.

## Data Model

### Entities (per project)
       
**Projects** - name, scope (small/medium/large), priority (High/Medium/Low), phase (Research/Design/Development), deadline, notebook history (`notebookHistory`: messages `{ id, createdAt, mode: process|ask, text, answer, status: processing|done|error|saved, error, outcomes[] }`). Last-worked date is recorded automatically. Canvas layout (`canvas`: `{ positions: { "<collection>:<id>": { x, y } }, colors: { "<collection>:<id>": "#rrggbb" }, frames: [{ id, title, x, y, width, height, color }], viewport: { x, y, zoom } }`) is stored on the project. The legacy plain-text `notebook` field is read as the first history message ("original notebook") and moved into the history on the next message.

**Goals** - code, name, description, metrics

**Stakeholders** - name, description, influence level, interest level (Mendelow matrix), attitude to the project (positive/neutral/negative), communication plan (how often, which channel, what they need to know)

**Competition** - name, description, competitor type (direct/indirect), strengths, weaknesses, inspiration

**Hypotheses** - code, name, description, status (untested/tested/refuted), explanation

**Personas** - code, name, status (protopersona/persona), description, motivation, needs, problems, barriers, characteristic quote, target group size, target group value

**Scenarios** - code, name, description, trigger (when the need arises), outcome (when the need is satisfied), frequency, value, MoSCoW rating

**Requirements** - code, name, description, motivation, category (data / function / quality / constraint), MoSCoW rating, explanation (for "Won't have")

**Risks** - code (RSK-…), name, description, likelihood (high/medium/low), impact (high/medium/low), mitigation, status (open/mitigated/occurred/closed). Typically captured at the kick-off or a pre-mortem. Not synchronised to the Flexi API (no server collection).

**Activities** - configurable task templates with checklists & deadlines. The built-in catalogue (31 techniques grouped as project / UX research / UX design: kick-off, deep dive, pre-mortem, desk research, stakeholder interviews and map, competitive and heuristic analysis, content audit, screener, interviews, survey, behavioural segmentation, personas, value proposition canvas, top tasks, journey mapping, requirements, context scenarios, prioritisation workshop, card sorting, information architecture, tree testing, design studio, low-fi prototyping, wireframing, usability testing, functional specification, handoff, retrospective) is distilled from the design team's internal technique library; every type carries a methodology (why, when, duration, who, steps, outputs) shown on the activity detail: the type description followed by why / when / duration / who directly under the activity name (above notes, status and deadline); steps and outputs in a collapsible "How to" box above the checklist. Only the original 13 types are created automatically for a new project (configurable per template). Each checklist follows the “How to” steps in the same order (every item is a verifiable outcome of a step). Checklist item ids of existing types never change, so stored activities keep their progress (an activity keeps the checklist it was created with); each checklist item may spawn a linked **Task** (the checklist row remains); the new task is automatically added as a connection to the activity (`checklistItemTaskIds` maps checklist item id → task id). **Assign task** (UI: „Zadat úkol“) from an activity (project list or activity header) opens the same **Add task** dialog as the Tasks section, with the task **name prefilled from the activity name**; on Save the task is created and linked only via **EntityConnections** (no checklist item link). Creating from a **checklist row** still uses the same Add task dialog with the step label as the prefilled name and keeps the checklist item link. Opening an already linked checklist task goes to the task detail page.

**Tasks** - SMART goals with due dates & assignees

**Bugs** - issue tracking with severity/impact/priority

**Team Members** - project team roster with roles



### Relationships (many-to-many, no cascading deletion)
 Arbitrary connections between any entities via `EntityConnections`. The connections panel **hides** rows where the linked entity was deleted (no placeholder row); orphan records may still exist in stored data until manually pruned or a future cleanup.



## Plugin System
Event-driven plugin registrywith capabilities and event bus.
       
       
**Built-in plugins:**

**data-status** - tracks last sync timestamp

 **tauri-local-api** - HTTP API server on localhost (desktop <-> Figma communication)
       
**flexi** - optional sync to Flexi API backend

**openai** - ChatGPT integration (notebook processing `ai:notebook`, notebook questions `ai:ask`, connection suggestions)

**gemini** - Google Gemini AI (same capabilities as OpenAI)

**ai-shared** - shared AI utilities (key management, prompts)


## Key Features
Project screens layout: every screen inside a project (project detail, activity detail, artifact lists and artifact details) starts with a full-width header – project colour, breadcrumb navigation (no large page title; breadcrumb items are links only, the project is edited from the menu), screen actions (Import, Export, menu) aligned right. Project metadata (priority, scope, last activity) is shown only in the project list. Below it the selected screen fills the left half of the width and the **Notebook** chat the right half (sticky while scrolling, same content and behaviour everywhere, unsent draft kept when navigating within the project). On narrow screens the chat moves below the content. The content column starts with a column heading styled like "Notebook": entity lists show the plural section name (e.g. "Personas") with the add button aligned right; entity and activity details show "<type> <name>" (e.g. "Persona Jana"; activities "Activity: <name>") – clicking the heading (pencil on hover) renames the entity – with the editable code below it where the entity has one (stakeholders show their strategy badge there).
Project detail: the left half is split evenly between the **Activities** list (status and checklist progress under each activity name) and the **Artifacts** list (one row per section – personas, scenarios, requirements, … – with counts, linking to each section).
Notebook chat: the user sends a text message (Ctrl+Enter); every message is kept permanently in the project's notebook history (no editing or deletion). A select left of the send button switches between two modes: **Ask** (button "Send question") – AI only answers in text using the project's data (all entities incl. activities, tasks, bugs, their custom fields, and for every item its connections from **EntityConnections** – items without connections are explicitly marked as having none; legacy ID-list fields such as `scenarioIds` are not used) and earlier notebook messages; it never writes to entities or anywhere else (only the question and answer are kept in the history); requires AI. **Enter information** (button "Process") – the processing flow below. If AI is available, the message is processed and the proposed create/update actions are reviewed in a dialog (confirm / skip each, or all); actions left unconfirmed when the dialog closes count as skipped. The AI reply under the message summarises the outcome (written / skipped per entity). Long messages and replies are shortened to a few lines; clicking them (or "Show all") expands them. The history scrolls without a visible scrollbar and stays at the newest message. Messages of any length can be processed: long text is sent to the AI in parts (by paragraphs, ~6000 characters each) and the proposals are merged (the same record from several parts becomes one action); the AI is asked for a JSON response with short source quotes only, a truncated response still yields all complete actions, a failed part is retried once and, if it still fails, the message shows which share of the notes was not processed. Without AI the message is just saved. Failed or interrupted processing can be retried. All AI outputs (proposed field values, answers, connection notes, competitor descriptions) are written in the language the user wrote in (notes, question, topic or entity texts); they are never translated to English – only JSON keys and enum values stay in English. Czech is detected by its diacritics and named explicitly in the prompt; otherwise the AI is told to keep the user's language.
Project list: compact tasks-count tag links to the project’s Tasks section (if any tasks are overdue, URL may include `?overdue=1` to turn on the overdue filter). Tasks list: **by default the “incomplete” filter is on** (only incomplete tasks); **filter and search text persist in memory per project for the browser tab session**, so returning from a task detail restores the same filters. Incomplete overdue items are visually emphasized; “Prošlé” filter matches any task whose due date is in the past. Multi-select list filters (tasks, bugs, requirements, personas, hypotheses, scenarios) use **OR**: an item appears if it matches **at least one** active badge.
Activity recommendations: the Activities panel suggests up to three techniques the project does not have yet (incl. removed ones), based on the state of artifacts – no risks → pre-mortem, no or incomplete stakeholders → stakeholder analysis, no competitors → competitive analysis, no personas → personas, personas without a connected scenario → scenarios, uncategorised requirements → requirements, five or more requirements with identical priority → prioritisation workshop, untested hypotheses → usability testing. Each suggestion shows its reason and an Add button.
AI methodology: notebook processing prompts follow the technique library rules (requirements as needs not solutions with a category, hypotheses as "I think that … because …", scenarios with trigger and outcome, stakeholder attitude, direct/indirect competitor, risk mitigation). In Ask mode the methodology of the project's activities is added to the context so the AI can answer how-to questions.
Project change history: every user change in a project (create, edit, delete of any record incl. connections, reordering, moves between projects, imports and confirmed AI proposals) is recorded per project – one history entry per user action (all changes made by that action together), with the full before/after state of each affected record. Automatic fields (`updatedAt`, `lastWorkedAt`, `_ts`), the notebook chat history and the canvas layout are not recorded; changes coming from sync are not recorded. The "History" screen (link in the header of every project screen) lists entries newest first with a summary, the changed fields and a "Revert" button. Reverting applies the inverse changes to the current state (created records are removed, deleted records come back, edited fields get their previous values while later edits of other fields are kept) and is itself recorded as a new entry, so a revert can be reverted again; the reverted entry is marked as reverted. History keeps the last 100 entries per project and is stored separately from the app data (key `uxlog_history`, mirrored to the desktop storage). A deleted project keeps its history; the project list shows "Deleted projects" with a "Restore" button that brings the project back with all its records.
Export files: in the desktop app a downloaded export is saved to Documents/UXLog and shown selected in the system file manager (PDF is opened in the default viewer); a toast shows the full path, or the reason when saving failed. Copying to the clipboard confirms with a toast. The export YAML quotes map keys that are not simple identifiers; the importer also reads older exports where such keys (e.g. `personas:<id>`) were written unquoted.

Project views: inside a project the app header shows a three-button switch right of the "UXLog" logo – **Data** (the screens with entities and the Notebook; it returns to the last data screen visited in that project, the project detail by default), **Canvas** and **Document**. Project document: the whole project data rendered as one readable document that fills the window below the app header (no screen header or Notebook): the project name as the main heading with scope, priority, phase and deadline below it (read-only), then one section per record type in the order of the project overview (personas, scenarios, requirements, hypotheses, risks, bugs, goals, stakeholders, competition, team, tasks, activities except removed ones; empty sections are left out) with a table of contents on wide screens, every record as a sub-heading (code links to its detail in Data) followed by its short attributes as a property list (select, text, date, number with unit) and its long text attributes as a small heading + paragraph; attributes follow the entity attribute configuration (hidden, custom and conditional attributes included). Empty attributes are hidden unless "Show empty fields" is on. Editing happens directly in the text: the project name, record names, text attributes and paragraphs are editable in place (plain text; Enter confirms a one-line field, Enter adds a line break in a paragraph and Ctrl+Enter confirms, Esc reverts); a change is saved when the field is left – into the record itself, exactly like an edit in the detail (change history, last-worked date); an empty name is not saved and leaving a field without a change saves nothing. Select, date and unit attributes are edited with an inline picker. Search: a search box in the document toolbar (Ctrl+F) finds every occurrence in the document regardless of letter case and diacritics, highlights all of them, marks the current one, shows "current / total" and moves between them with Enter / Shift+Enter or the arrows. Export: "Export to Markdown" copies the document to the clipboard or downloads it as a `.md` file (# project, ## section, ### record, short attributes as a "**Label:** value" list, long attributes as #### heading + paragraph; empty attributes left out; record texts are written as they are, so Markdown in them is kept). The document itself is never stored – it is always derived from the data. Project canvas: a Miro-like infinite board of the project that fills the whole window below the app header (no screen header, breadcrumbs or Notebook – an unsent Notebook draft is kept for the return). Floating controls: a type filter centred on the top edge ("Highlight": "All types" plus every card type with its number of cards in the project, types without cards are disabled) – choosing a type makes all cards of other types nearly transparent (15 % opacity) so the chosen type stands out (only the look changes: dimmed cards can still be selected, moved and opened; the filter is not saved and resets when switching projects); a one-line control legend in the bottom-left corner; selection count, zoom −/+ with the zoom level and "Fit all" in the bottom-right corner. The default view and "Fit all" keep the strip under the filter free of cards. Frames: the "Frame" tool in the top-left corner (shortcut F, Esc cancels) lets the user draw a rectangle on the board (a click without dragging inserts a 520 × 320 frame; minimum 160 × 120); a new frame gets the title "Frame n" and immediately offers renaming. A frame is a titled area behind the cards; its title sits above its top edge. A card belongs to a frame when the card's centre lies inside it, so a card is put into a frame simply by dragging it there; frames don't store their cards. Dragging the title moves the frame together with its cards and with frames lying completely inside it (one save on release); clicking the title selects the frame (card selection is cleared), double-click or F2 renames it (an empty title is not saved), the corner handle of a selected frame resizes it. The frame body does not react to the pointer, so selection rectangles, panning and card dragging work inside frames. A selected frame shows the same floating toolbar as cards: frame color (tinted background and colored border, palette shared with cards) and a menu with "Rename" and "Delete frame" (Delete key works too); deleting asks for confirmation and never deletes the cards. Smaller frames are drawn above bigger ones. "Fit all" includes frames. Frames are part of the canvas layout: not recorded in the change history, no change of the last-worked date, not part of export/import. Every project record (goals, stakeholders, team members, competitors, hypotheses, personas, scenarios, requirements, risks, activities except removed ones, tasks, bugs) appears as a square card with its type, code, a priority tag at the right end of that row (requirements and scenarios: MoSCoW, shown short as Must / Should / Could / Won't, missing = Could; bugs: the priority computed from severity and impact, only when both are set; colored by level: must/critical red, should/high orange, could/medium yellow, won't/low grey), name (long names wrap to several lines, never truncated) and the beginning of its description filling the rest of the card (fading out where it does not fit). A card without a saved position is placed in its type's column (one column per type present in the project, cards stacked in list order). Selection: clicking a card selects it (Shift/Ctrl+click adds or removes it), dragging on empty space draws a selection rectangle that selects every card it touches (with Shift/Ctrl it adds to the selection), clicking empty space or Esc clears the selection, Ctrl+A selects all; selected cards are highlighted. Selection toolbar: while one or more cards are selected, a small floating toolbar is shown centred above the selection (below it when there is no room above without covering the type filter, just under the filter when there is room neither above nor below); it follows panning and zooming and hides while cards are dragged or a selection rectangle is drawn. It has two tools: **Card color** – a palette (configurable in `data/app.yaml`, `canvasCardColors`) plus "No color"; the chosen color becomes the card background and the text color switches automatically between dark and white, whichever has the higher contrast (WCAG), secondary text and border are derived from it; the button shows the selection's common color, or a multicolor swatch when the selected cards differ. Card color is a canvas-only property of the project's layout (not of the record), is not recorded in the change history and does not change the last-worked date. **Actions menu (…)** – the same actions as the record detail: "Move to another project", "Copy to another project" (the same project picker dialog, applied to all selected records) and delete (with the record's own label and confirmation for one card, "Delete selected (n)" with a count confirmation for more); deleting several records is one history entry that can be reverted. Moving a record to another project drops its canvas position and color in the source project. Moving: dragging a card moves it, dragging a selected card moves the whole selection; the arrow keys move the focused card or the selection (Shift for a bigger step). Positions are saved when the drag ends and kept. Panning: right or middle mouse button drag, or Space + drag; the mouse wheel zooms around the cursor (20–250 %), the floating buttons zoom in/out and "Fit all" shows every card; the last pan/zoom is remembered per project. Double-clicking a card (or Enter on a focused card) opens the record's detail in a floating window over the board – the user stays on the canvas and the board remains usable. Every opened record gets its own window (opening an already open record only brings its window to the front); new windows appear near the top-right corner, each next one cascaded down-left so it never exactly covers another. A window (default 560 × 480 px, smaller on a small screen) can be moved by dragging its title bar and resized by dragging its bottom-right corner (minimum 360 × 240 px; its title bar always stays on the board); clicking a window brings it to the front. The window shows the full detail with all its editing, connections and actions except import and export (move/copy, delete); deleting or moving the record away closes its window, a link to a connected record opens that record in another window. The title bar shows type, code and name, the record's actions menu and Close; Esc closes the focused window. Windows are not saved – leaving the canvas closes them; windows of records deleted elsewhere disappear. Moving cards and the board does not change the project's last-worked date and is not recorded in the change history; positions of deleted records are dropped. Canvas layout travels inside the exported project record (map keys such as `personas:<id>` are written quoted), but import ignores it.
